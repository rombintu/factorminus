# ТЗ. Этап 1 (альтернатива): данные и запуск, просто и быстро

Это MVP для хакатона, а не продакшен. Нужен маленький понятный код: человек должен прочитать его за вечер и легко отлаживать.

## Зачем переписываем

Первая версия лежит в ветке `stage-1` (PR #1) и работает. Но для MVP она тяжёлая:
- около 11 тыс. строк: 3 тыс. кода, 3 тыс. тестов, 2,4 тыс. lock-файлов с хэшами, остальное — скрипты, workflow, Docker;
- 4 цели Docker, 4 сервиса compose, 4 workflow;
- образ с ML собирается долго, ML-проверки в CI идут долго;
- отдельная база для синтетики, кассеты, миграции, переменные путей.

Ты делаешь этап заново в новой ветке `stage-1-alt`, с теми же продуктовыми возможностями, но в разы компактнее. Потом две версии сравнят.

**Код из ветки `stage-1` не открывай и не копируй.** Нужна независимая реализация. Брать оттуда можно только данные, перечисленные в разделе «Что взять из старой ветки».

## Правила простоты (главное в этом ТЗ)

1. **Бюджет строк, жёсткий:**

   | Что | Предел |
   |---|---|
   | `src/` (без сертификата и CSV) | 1200 |
   | `tests/` | 800 |
   | `Dockerfile` + `compose.yaml` + `Makefile` + `.github/workflows/ci.yml` + `pyproject.toml` | 150 |
   | папка `scripts/` | не создавать |

   Если не укладываешься, упрощай решение, а не сжимай код в одну строку.
2. **Плоская структура**, примерно 10 модулей. Функции вместо классов, где класс не нужен. Никаких абстрактных базовых классов, Protocol, фабрик, плагинов, «на будущее». Функция до 40 строк, модуль до 300.
3. **Минимум зависимостей:** `httpx`, `pydantic`, `numpy`. Для разработки: `pytest`, `ruff`. CLI на `argparse`, `.env` — простой парсер на 10 строк, конфиги — CSV и stdlib. Каждую новую зависимость обоснуй в отчёте.
4. **Одна база:** `data/fm.sqlite`. Реальные и синтетические данные лежат в одних таблицах, синтетика отличается `id` вида `SYN_*` и полем `source='synth'`. Отдельных баз для синтетики или тестов нет. Тесты работают с временным файлом или `:memory:`.
5. **База — это кэш.** Миграций нет: `schema.sql` с `CREATE TABLE IF NOT EXISTS`. Если схема изменилась, файл удаляется и данные загружаются заново (`fm reset`).
6. **Никакого ML на этом этапе.** laya, torch и ML-образ не ставить и не упоминать в коде.
7. **Отладка прежде всего.** Должно быть легко понять, что произошло:
   - `fm call <tool> '<json>'` печатает сырой ответ MCP (только инструменты белого списка);
   - `-v` печатает в stderr каждый вызов MCP: инструмент, аргументы, время;
   - в `instruments` и `brands` хранится `raw_json` ответа;
   - ошибки понятные, без трейсбека для ожидаемых случаев (нет токена, бумага не найдена).
8. **Тесты — по делу.** Тест пишется на поведение, которое может сломаться, а не на каждую функцию. Без сети, `pytest -q` за 15 с или быстрее.
9. **Не добавлять:** lock-файлы с хэшами, скрипты гигиены, pre-commit, dependabot, шаблоны PR, журнал этапов, релизы, GHCR, multi-arch, отдельные workflow, закрепление actions по SHA, record/replay-кассеты, переменные путей (`FM_HOME` и подобные).

Если модуль разросся за 300 строк, его можно разделить. Новые слои и папки не вводить.

### 2. Конфигурация (`config.py`)

- `TINVEST_TOKEN` берётся из окружения, если там нет — из `.env`. Нужен только командам, которые ходят в MCP. Без токена понятная ошибка «задайте TINVEST_TOKEN в .env».
- `TINVEST_MCP_URL`: по умолчанию песочница `https://sandbox-invest-public-api.tbank.ru/mcp`. Разрешён только `https://` и хост `*.tbank.ru`, иначе ошибка: токен не должен уйти на чужой адрес.
- `FM_DB`: по умолчанию `data/fm.sqlite`.
- `tls_context()`: certifi плюс корневой сертификат из пакета. Отпечаток сверяется при создании контекста, при несовпадении — ошибка. http не используется нигде. Флага отключения TLS нет.
- Токен не попадает в `repr`, логи и вывод.

### 3. MCP-клиент (`mcp.py`)

- `httpx`, таймаут 30 с.
- `initialize` → `notifications/initialized` → `tools/call`, заголовок `Mcp-Session-Id`.
- Ответ в JSON или SSE: берётся `data:` с нужным `id`, JSON из `result.content[]` разбирается. `isError` или JSON-RPC `error` превращаются в понятное исключение.
- **Белый список из 9 инструментов:** `invest_find_instrument`, `invest_get_share`, `invest_get_etf`, `invest_get_bond`, `invest_get_currency`, `invest_get_asset`, `invest_get_brand`, `invest_get_candles`, `invest_get_risk_rates`. Остальные отклоняются **до** сетевого запроса.
- Пауза 0,33 с между вызовами. 3 попытки на 429, 5xx и сетевые ошибки. Одна переинициализация, если сессия истекла.

### 4. Загрузка данных (`ingest.py`, `iss.py`, `db.py`)

Таблицы в `schema.sql`, без лишних:
- `instruments`: `id` (`TICKER_CLASSCODE` или `SYN_*`), ticker, class_code, kind, role, index_id, name, isin, lot, currency, asset_uid, brand_uid, uid, first_candle, maturity, dlong, dshort, source, raw_json, updated_at;
- `brands`: uid, name, company, sector, description, country, source, raw_json, updated_at;
- `candles`: instrument_id, date, open, high, low, close, volume, первичный ключ (instrument_id, date);
- `index_weights`: index_id, date, ticker, weight.

Если для этапа 2 очевидно нужно ещё поле, добавь и запиши в отчёт.

`fm ingest [--only ID,ID] [--since 2020-01-01]` для каждой бумаги из `universe.csv`:
1. `get_share|etf|bond|currency` → `instruments`;
2. `get_asset` → `brand_uid`, `get_brand` → `brands`. Один бренд — один вызов;
3. дневные свечи с 2020-01-01 (или с первой свечи). При повторном запуске догружаются только новые дни;
4. `get_risk_rates` пачками → `uid`, `dshort`, если в карточке пусто.

Требования:
- ошибка на одной бумаге не останавливает загрузку: печатается и попадает в сводку;
- в конце сводка: бумаги, бренды, свечи, ошибки, время;
- повторный запуск не дублирует строки.

`fm weights` → веса IMOEX из ISS в `index_weights` (публичный запрос, без токена).

### 5. Синтетический рынок (`synth.py`, команда `fm synth`)

Нужен для тестов и демо без токена. Пишет **прямо в ту же базу** (`source='synth'`). Перед записью удаляет старую синтетику.

С фиксированным seed генерирует:
- бумаги `SYN_*` с брендами, секторами и описаниями на русском;
- около 1500 торговых дней цен из факторной модели `r = β·рынок + Σγ·фактор + шум`. Факторы: рынок, нефть, банки, металлы, технологии, ставка, золото;
- индекс `SYNIDX` с весами (сумма 100%).

Обязательные свойства — на них этап 2 построит контрольные кейсы:
- два фонда-близнеца на `SYNIDX` (корреляция ≥ 0,95);
- скрытый дубль: третий фонд на тот же индекс без слова «индекс» в названии и описании;
- «дивидендный» активный фонд, на 70% из нефти и банков;
- 4–5 нефтяных акций (взаимная корреляция 0,6–0,8);
- 3 банка, среди них пара «обыкновенная + привилегированная» с общим брендом;
- золото с корреляцией к рынку около нуля или отрицательной;
- фонд денежного рынка с почти нулевой волатильностью;
- 2 ОФЗ с разной чувствительностью к ставке;
- акция с историей 40 дней;
- 3 шока рынка (30, 20 и 150 дней). В шоки пара «синтетический Сбер — синтетический ВТБ» коррелирует сильнее 0,8, а в обычные дни слабо (0,3–0,5 после вычета рынка);
- группа из 3–4 компаний (материнская и дочерние, включая облигацию дочки);
- id одной бумаги, которой нет в базе (для флага `preliminary` на этапе 2).

Ожидаемые свойства хранятся словарём в `synth.py` (`EXPECTED`) и проверяются тестом. Сгенерированные файлы в git не кладутся: генерация быстрая, тесты делают её сами.

### 6. Контракт (`contract.py`, `wording.py`)

- Pydantic-модели запроса и ответа по разделу 7 `CONTEXT.md`, с перечислениями `verdict`, `severity`, `flags`, `operation`.
- Проверки: `amount_rub > 0`, стоимость позиций ≥ 0, формат `instrument_id`, доли 0–100, сумма `factors_*` около 100.
- 5 примеров ответа в `docs/contract/examples/`: `duplicate`, `increases_skew`, `reduces_skew`, `neutral`, `unavailable`. Тест: все валидны.
- `wording.py`: линтер, который ловит советы («купите», «продайте», «рекомендуем», «советуем», «лучше», «стоит»). Этап 2 будет прогонять через него все вердикты.

### 7. CLI (`fm`, argparse)

| Команда | Что делает |
|---|---|
| `fm demo` | `synth` + `stats`, работает без токена и без сети |
| `fm synth` | синтетика в базу |
| `fm check` | рукопожатие с MCP, все 9 инструментов есть на сервере |
| `fm ingest [--only] [--since]` | загрузка вселенной |
| `fm weights` | веса IMOEX |
| `fm stats` | число строк по таблицам, диапазон дат свечей, отдельно real и synth |
| `fm call TOOL JSON` | сырой ответ MCP для отладки |
| `fm find QUERY` | поиск бумаги, чтобы пополнять `universe.csv` |
| `fm reset` | удалить базу |

### 8. Docker

- Один `Dockerfile`: `python:3.12-slim`, uv из образа `ghcr.io/astral-sh/uv` с точной версией, `uv sync --frozen --no-dev`. Сначала слой зависимостей, потом код, пользователь не root. Тестов и ML в образе нет.
- `compose.yaml`: один сервис `app`, bind-mount `./data:/app/data` (база видна на диске, её можно открыть любым SQLite-клиентом), `env_file: .env` с `required: false`. По умолчанию команда `fm demo`.
- `.dockerignore`: в контекст сборки не попадают `.env`, `data/`, `.git`, `.venv`.
- **Цели по скорости** (замерить и записать в отчёт):
  - `docker build --no-cache .` при уже скачанном базовом образе — **до 30 с**;
  - пересборка после правки кода — до 5 с;
  - `docker compose run --rm app` (демо) — до 10 с;
  - образ — до 250 МБ.

### 9. CI (`.github/workflows/ci.yml`, один файл)

На push и PR:
1. `uv sync`;
2. `ruff check` и `ruff format --check`;
3. `pytest -q`;
4. `docker build` и `docker run --rm <образ> fm demo`.

Весь прогон — до 3 минут. Live-тестов и токена в CI нет. Защита от утечки — один тест в `pytest`: ни один файл в git не содержит строку вида `t\.[A-Za-z0-9_-]{80,}`.

### 10. Тесты (без сети)

Достаточно таких:
- MCP-клиент на `httpx.MockTransport`:
  - рукопожатие;
  - SSE с несколькими событиями;
  - `isError`;
  - ретрай на 429;
  - инструмент вне белого списка отклонён, а запрос не отправлен;
  - токена нет в логах;
- разбор чисел MCP: `{"units","nano"}`, `{"value"}`, строки;
- `fm ingest` против фейкового MCP с 2–3 синтетическими бумагами: база заполнена, повторный запуск не дублирует строки;
- `config`: адрес не `https` или не `*.tbank.ru` → ошибка; подменённый сертификат → ошибка;
- синтетика: одинаковый seed даёт одинаковые данные, свойства из `EXPECTED` выполняются;
- контракт: примеры валидны и проходят линтер, неверные значения отклоняются;
- нет токена в файлах git.

Live-тест (`pytest -m live`, по умолчанию пропускается): каждый из 9 инструментов вызывается на песочнице и возвращает непустой ответ. Ответы не печатаются и не сохраняются.

### 11. Живая проверка (токен песочницы уже в `.env`)

1. `fm check`;
2. `fm ingest` по всей вселенной;
3. `fm weights`;
4. `fm stats`;
5. `pytest -m live`.

Если токен отклонён (401 или `40003`), запиши это в отчёт как непроверенное и продолжай.

## Критерии приёмки

1. Бюджет строк соблюдён. В отчёте вывод `wc -l` по `src/`, `tests/` и инфраструктуре.
2. `make lint`, `make test` зелёные, тесты идут 15 с или быстрее и не ходят в сеть.
3. Цели Docker из п. 8 выполнены, замеры с командами и выводом `time` есть в отчёте.
4. CI зелёный и укладывается в 3 минуты.
5. `fm demo` работает без токена и без сети. Синтетика лежит в той же `data/fm.sqlite`.
6. Живая проверка: в базе не меньше 50 бумаг вселенной с брендами и секторами, свечи с 2020 года для большинства из них, веса IMOEX. Вывод `fm stats` и время полной загрузки в отчёте.
7. В git нет `.env`, `data/` и реальных цен.
8. Отчёт `docs/reports/STAGE_1_ALT_REPORT.md`, не длиннее 150 строк:
   - что сделано;
   - замеры (строки, время тестов, сборки, CI, размер образа, число зависимостей);
   - что не сделано и почему;
   - бумаги вселенной, которые не нашлись;
   - вопросы к этапу 2.
