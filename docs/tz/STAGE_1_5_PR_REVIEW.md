## 1. TLS: http не используем, оставляем один корневой сертификат в пакете

**Проверено:**
- `http://invest-public-api.tbank.ru/mcp`: порт 80 принимает соединение, но не отвечает (таймаут 10 с). MCP по http не работает.
- Даже если бы работал, токен передаётся в заголовке `Authorization`. По http его прочитает любой в той же сети, например на Wi-Fi площадки. Токен даёт доступ к брокерскому счёту.
- ISS по http отвечает (200). Но тогда состав индекса можно подменить по пути, а выигрыша нет: https работает.
- Боевой сервер T-Invest, песочница и ISS сами присылают всю цепочку: сертификат сайта → Sub CA → Root CA. Python `ssl` с набором certifi и одним корневым сертификатом проходит на всех трёх хостах. С одним только certifi получаем `CERTIFICATE_VERIFY_FAILED`. Значит, Sub CA в репозитории не нужны.

**Сделать:**
1. Удалить `certs/russian_trusted_sub_ca_2027.pem`, `certs/russian_trusted_sub_ca_2029.pem` и папку `certs/`.
2. Корневой сертификат перенести в пакет: `src/factorminus/certs/russian_trusted_root_ca.pem`, через `package-data`. В docstring модуля, который его загружает, одной строкой указать: источник (Госуслуги), SHA-256 и срок действия (до 2032).
3. Убрать сборку бандла:
   - `scripts/build_ca_bundle.py` и `tests/test_build_ca_bundle.py`;
   - стадию `ca` в Dockerfile, `COPY certs` в образе `test`;
   - цель `ca-bundle` в Makefile;
   - `TINVEST_CA_BUNDLE` из `config.py`, `compose.yaml`, ENV Dockerfile, `.env.example`, `docs/DEPLOY.md`.

   Вместо этого одна функция:
   ```python
   ROOT_CA_SHA256 = "d26d2d0231b7c39f92cc738512ba54103519e4405d68b5bd703e9788ca8ecf31"

   def tls_context() -> ssl.SSLContext:
       pem = (files("factorminus") / "certs/russian_trusted_root_ca.pem").read_text("ascii")
       if hashlib.sha256(ssl.PEM_cert_to_DER_cert(pem)).hexdigest() != ROOT_CA_SHA256:
           raise ConfigError("Russian Trusted Root CA: отпечаток не совпадает, файл подменён")
       ctx = ssl.create_default_context(cafile=certifi.where())
       ctx.load_verify_locations(cadata=pem)
       return ctx
   ```
   `Settings.ssl_verify()` возвращает `tls_context()`, а при `TINVEST_INSECURE_SSL=1` по-прежнему `False`. MCP-клиент и ISS получают контекст через неё, как сейчас.
4. `certifi` импортируется напрямую, поэтому добавить его в `dependencies` в `pyproject.toml`. Если `base.txt` изменится, перегенерировать lock-файлы через `make lock`, `make lock-check` должен быть зелёным.
5. Тесты вместо `test_build_ca_bundle.py`:
   - контекст строится из файла пакета;
   - подменённый PEM даёт `ConfigError`;
   - в `check_image.sh` для `runtime` выполняется `python -c "from factorminus.config import tls_context; tls_context()"`. Так проверяем, что файл попал в колесо.
6. Обязательный `https://` в `TINVEST_MCP_URL` не трогать. Если теста на `http://` → `ConfigError` нет, добавить.
7. Гигиену, `.gitleaks.toml` и `docs/DEPLOY.md` (строка про `CERTIFICATE_VERIFY_FAILED`) поправить под новый путь.

## 2. «Удалить ключи и вычистить коммиты»: история не переписывается

**Проверено:**
- В `certs/` лежали три открытых **сертификата** (`BEGIN CERTIFICATE`), закрытых ключей там нет. Это публичные сертификаты НУЦ Минцифры. Их раздают Госуслуги, они встроены в Яндекс Браузер. Секрета в них нет.
- Все 48 коммитов `origin/main` и `origin/stage-1` проверены на токен `t\.[A-Za-z0-9_-]{80,}` и на `PRIVATE KEY`: совпадений нет. Файла `.env` нет ни в одном коммите. gitleaks в CI проверяет всю историю (`fetch-depth: 0`).
- Переписывание истории публичного репозитория сломает PR #1 и ссылки на коммиты в отчётах. Уже сделанные клоны и форки при этом останутся. Такой шаг оправдан только при утечке настоящего секрета, а её нет.

**Сделать:** только п. 1, файлы Sub CA удаляются обычным коммитом. `git filter-repo`, `filter-branch` и force-push не использовать.

## 3. Проверка инструментов MCP: на песочнице и только тех, что используются

**Проверено:**
- В белом списке 16 инструментов, а код вызывает 9: `find_instrument`, `get_share`, `get_etf`, `get_bond`, `get_currency`, `get_asset`, `get_brand`, `get_candles`, `get_risk_rates`.
- Остальные 7 (`get_asset_fundamentals`, `get_market_values`, `get_trading_statuses`, `get_news`, `list_shares`, `list_etfs`, `list_bonds`) нигде не вызываются, в ТЗ этапа 2 их тоже нет.
- `make test-live` вызывает 6 из 9 инструментов. Без проверки остаются `find_instrument`, `get_currency` и `get_risk_rates`.
- Песочница `https://sandbox-invest-public-api.tbank.ru/mcp` доступна: без токена отвечает 401. Её хост проходит проверку `*.tbank.ru`.
- Токен песочницы не видит реальные счета, поэтому при утечке он опасен меньше. Т-Банк рекомендует песочницу для экспериментов.
- Документация песочницы (developer.tbank.ru/invest/intro/developer/sandbox, раздел «Песочница и prod»):
  - рекомендованный способ — вызывать те же методы по адресу песочницы;
  - сервис инструментов и сервис котировок в песочнице есть. Значит, карточки, активы, бренды, поиск и свечи должны работать;
  - **«в песочнице не рассчитываются … ставки риска»**. Поэтому `invest_get_risk_rates` может вернуть пустой ответ.

  В пайплайне ставки риска вспомогательные: они только дописывают `uid` и `dshort` в карточку, если те пустые. При пустом ответе каждый сбор будет писать ошибку `risk_rates`.
- Предварительная проверка 25.11 с токеном песочницы. Токен принят. `get_share`, `get_asset`, `get_candles` (`SBER_TQBR`, 14 дней) и `get_risk_rates` отвечают, ставка риска пришла непустой. Полный прогон всех 9 инструментов остаётся за агентом. Токен песочницы и её адрес уже лежат в `.env`.

**Сделать:**
1. Сократить `READ_ONLY_TOOLS` до 9 используемых. Новый инструмент добавляется только вместе с кодом, который его вызывает, и с live-проверкой.
2. Обновить упоминания «16 инструментов» в README и `docs/CONTEXT.md`. В отчёте этапа 1 старый текст не переписывать, добавить пометку «сокращено до 9, см. отчёт 1.5».
3. Smoke в `tests/test_live.py`:
   - словарь `SMOKE_ARGS: dict[str, dict]` с минимальными аргументами для каждого инструмента из `READ_ONLY_TOOLS`;
   - параметризованный тест вызывает каждый инструмент и проверяет, что ответ не ошибка и одно характерное поле на месте и не пустое. Пустой ответ считается провалом: так ловится случай со ставками риска;
   - ответы не печатать, не сохранять и кассеты не записывать.
4. Офлайн-тест, который идёт в обычном CI без сети: `set(SMOKE_ARGS) == READ_ONLY_TOOLS`. Так инструмент без live-проверки в список не добавить.
5. Прогон на песочнице:
   - пользователь выпускает **Sandbox token**: tbank.ru → настройки профиля Т-Инвестиций → «Токены T-Invest API» → токен для песочницы. Тип описан в developer.tbank.ru/invest/intro/intro/token. Страница MCP говорит, что подключение к песочнице такое же, отличается только адрес. Токен нужно использовать в течение 7 дней после выпуска, иначе его отзовут;
   - токен песочницы и `TINVEST_MCP_URL=https://sandbox-invest-public-api.tbank.ru/mcp` уже лежат в `.env`. Боевой `.env` сохранён в `.env.prod.bak`, его не трогать и не читать;
   - агент запускает `make test-live`. `.env` агент не открывает, токен не выводит.

   В отчёт: вывод pytest по каждому инструменту (passed/failed) и тесты ISS.
6. Если на песочнице проходят все 9 инструментов:
   - `DEFAULT_MCP_URL` и `.env.example` переключить на песочницу;
   - в `docs/DEPLOY.md` написать: «для сбора данных нужен токен песочницы, боевой не нужен».

   Если какой-то инструмент не проходит, записать в отчёт, какой именно и с какой ошибкой. Умолчание в этом случае не менять.

   Если MCP песочницы отклоняет токен (401 или `40003` на всех вызовах), записать это в отчёт. В `docs/DEPLOY.md` указать запасной вариант: боевой адрес и токен типа **«Только чтение»**. Он не может выставлять заявки, но видит портфель.

   В любом случае `docs/DEPLOY.md` должен называть тип токена, а не просто «токен».

   Если не проходит только `invest_get_risk_rates`, отладкой не заниматься: это ожидаемое поведение песочницы. Напиши в отчёте два варианта на выбор пользователя:
   - (а) оставить по умолчанию боевой адрес с токеном «Только чтение»;
   - (б) перейти на песочницу и убрать шаг `risk_rates` из пайплайна вместе с инструментом в белом списке. Тогда инструментов станет 8, а в отчёте нужно указать, сколько карточек в реальной базе сейчас получают `uid` и `dshort` именно из этого шага.

   Сам ничего из этого не выбирай.
7. По http ничего не проверять (см. п. 1).
