# ТЗ. Этап 1.5: CI/CD, Docker и контроль этапов

Сначала прочитай `docs/CONTEXT.md` целиком (особенно раздел 6 «Правила» и раздел 10 «Как работать») и `docs/reports/STAGE_1_REPORT.md`. Этот этап идёт **до** этапа 2. Логику анализа он не трогает: только инфраструктура, сборка, проверки и запуск.

## Цель этапа

К концу этапа:
1. Любой коммит в PR автоматически проверяется в GitHub Actions: линтер, тесты, гигиена репозитория (нет секретов и рыночных данных), сборка Docker-образа и запуск в нём демо на синтетике.
2. Проект поднимается одной командой на любой машине с Docker, без локального Python:
   - `docker compose run --rm demo` — работает **без токена**, на синтетике;
   - `docker compose run --rm fm <команда>` — любая команда CLI;
   - `docker compose run --rm nightly` — ночная загрузка реальных данных с токеном из `.env`.
3. Релиз этапа (тег `vX.Y.Z`) собирает и публикует образы в GHCR и создаёт GitHub Release с выдержкой из отчёта этапа.
4. Следующие этапы встраиваются в эту схему без переделок. Каждый этап — отдельный PR в `main` с зелёным CI, шаблоном PR, отчётом и записью в журнале этапов. Новые проверки добавляются в цели `Makefile`, а не в YAML.

## Порядок работы (обязательно)

1. **Ветки.**
   - Если `stage-1` ещё не влит в `main`, спроси пользователя. С его согласия влей локально: `git switch main && git merge --no-ff stage-1`.
   - Ветка этапа: `infra` от `main`.
   - Push и PR — **только после явного «да» пользователя** (CONTEXT, раздел 10). Без пуша CI на GitHub не проверить, поэтому в конце этапа спроси разрешение одним сообщением: что пушится, в какую ветку, какой PR открывается.
2. План и практики:
   - план → `docs/plans/STAGE_1_5_PLAN.md`;
   - код на Python (скрипты проверок, правки `config.py`) — по TDD.
3. Ревью **обязательны**:
   - security-review по Dockerfile, compose и всем workflow. Цели: секреты, права `GITHUB_TOKEN`, триггеры от форков, закреплённые версии;
   - code-review по всей ветке.
4. Проверка перед сдачей (`make ci`, Docker) → отчёт `docs/reports/STAGE_1_5_REPORT.md`.

## 1.5.0. Что обязательно учесть (иначе сломается)

Это особенности текущего кода. Проверь их сам, прежде чем писать Dockerfile.

1. **Корень проекта ищется по `pyproject.toml`.** `config._find_repo_root()` поднимается от `__file__`. При обычной (не editable) установке в образ пакет лежит в `site-packages`, `pyproject.toml` там нет, и корнем станет текущая папка. От корня зависят `data/universe.yaml`, `tests/fixtures/synthetic`, кассеты, путь к БД и `.env`.
   - Добавь переменную `FM_HOME`. Если она задана, это корень; иначе работает текущий поиск. Тест.
2. **Данные времени выполнения и файлы из git лежат в одной папке `data/`.** Если смонтировать том на `/app/data`, он закроет `data/universe.yaml`, а на этапе 2 и `episodes.yaml`, `groups.yaml`, `demo_portfolios.yaml`. Именованный том Docker заполняется из образа только при первом запуске. Значит, обновлённый `universe.yaml` в новом образе будет молча проигнорирован. Это тихая и опасная ошибка.
   - Добавь переменную `FM_DATA_DIR` (по умолчанию `<корень>/data`). Всё, что **пишется** во время работы, идёт туда: SQLite, кассеты record, логи, `universe_resolved.json`.
   - Всё, что **лежит в git**, читается из `<корень>/data` и в контейнере доступно только для чтения.
   - Пройди по `cli.py`, `mcp/client.py`, `config.py` и всем местам с `REPO_ROOT / "data"`, раздели пути. `FM_DB_PATH`, если задан, имеет приоритет. Тесты на оба режима.
3. **CA-бандл.** Сейчас `data/ca/ru-bundle.pem` (116 сертификатов: certifi + российские) лежит вне git, а `ssl.create_default_context(cafile=...)` доверяет **только** ему.
   - Закоммить в `certs/` только российские сертификаты, которых нет в certifi (корневой «Russian Trusted Root CA» и, если есть в бандле, промежуточный). Это публичные сертификаты, не секрет.
   - Скрипт `scripts/build_ca_bundle.py`: certifi + `certs/*.pem` → бандл. Перед сборкой скрипт сверяет SHA-256 корневого с зашитым значением `D2:6D:2D:02:31:B7:C3:9F:92:CC:73:85:12:BA:54:10:35:19:E4:40:5D:68:B5:BD:70:3E:97:88:CA:8E:CF:31` (сверено пользователем с официальными файлами Госуслуг). Не совпало — ошибка, а не предупреждение.
   - В образе бандл собирается при сборке, `TINVEST_CA_BUNDLE` указывает на него по умолчанию. Локально: `make ca-bundle` пишет `data/ca/ru-bundle.pem`, как сейчас.
   - Тест: отпечаток проверяется, подменённый файл отвергается.
4. **`.env` не попадает в образ и в слои.** Токен передаётся только при запуске: `env_file` в compose. Никаких `ARG TINVEST_TOKEN` и `ENV TINVEST_TOKEN` в Dockerfile, никакого `COPY .env`. `.dockerignore` закрывает `.env*` (кроме `.env.example`), `data/*` (кроме yaml-файлов конфигурации), `.git`, `.venv`, кэши и `*.sqlite`.
5. **Тесты не ходят в сеть** (`conftest.py` блокирует сокеты). В CI это сохраняется. Live-тесты в CI **не запускаются** (см. «Что НЕ делать»).
6. **`Makefile` вызывает `.venv/bin/python`.** В CI и в контейнере Python системный. Сделай `PY ?= python` с автоопределением: если есть `.venv/bin/python`, берётся он. Локальная работа не должна сломаться.
7. **Фикстуры синтетики зависят от версии numpy** (комментарий в `pyproject.toml`, тест `test_committed_fixtures_match_generator`). Версии в CI, в образе и локально должны совпадать. Отсюда lock-файлы (1.5.1).

## 1.5.1. Зависимости и воспроизводимость

1. Lock-файлы в `requirements/`, сгенерированные `uv pip compile` для Python 3.12 (uv только как инструмент компиляции, `pip` в Makefile остаётся рабочим):
   - `base.txt` — `dependencies`;
   - `dev.txt` — base + `dev`;
   - `ml.txt` — base + `ml`.
2. Для `ml.txt` torch берётся **CPU-сборкой** (`--extra-index-url https://download.pytorch.org/whl/cpu` или `--index` с явным правилом для torch). Иначе образ потянет CUDA на несколько гигабайт. В отчёт: итоговый размер ML-образа.
3. В `dev` добавь `pytest-cov`, `pre-commit`, `pip-audit`.
4. `make lock` перегенерирует lock-файлы. CI проверяет, что lock-файлы соответствуют `pyproject.toml`: перегенерация не даёт diff.
5. `make install` ставит из `requirements/dev.txt` + `-e .`. Проверь, что после этого `make test` зелёный на чистой `.venv`.

## 1.5.2. Docker

**`Dockerfile`** (многоступенчатый, одна точка правды для CI и запуска):

| Цель (`--target`) | Что внутри | Зачем |
|---|---|---|
| `runtime` | `python:3.12-slim` (тег + digest), зависимости из `base.txt`, пакет, `data/*.yaml`, `config/` (появится на этапе 2), `tests/fixtures/synthetic`, CA-бандл | Основной образ: CLI, nightly, демо, позже API |
| `runtime-ml` | `runtime` + `ml.txt` (torch CPU, laya) + заранее скачанные веса laya | Сборка разметки laya (`fm build` на этапе 2) |
| `test` | `runtime` + `dev.txt` + `tests/` | Прогон тестов в контейнере: `make docker-test` |

Требования:
- пользователь не root (uid 10001), `WORKDIR /app`, `FM_HOME=/app`, `FM_DATA_DIR=/var/lib/factorminus`;
- `PYTHONDONTWRITEBYTECODE=1`, `PYTHONUNBUFFERED=1`, `PIP_NO_CACHE_DIR=1`;
- слой зависимостей отдельно от слоя кода (кэш сборки), `--mount=type=cache` для pip;
- `ENTRYPOINT ["fm"]`, `CMD ["--help"]`;
- метки OCI: `org.opencontainers.image.source`, `revision`, `version`, `licenses`;
- веса laya в `runtime-ml` кладутся в образ при сборке (`HF_HOME` или кэш laya внутри образа). Тогда холодный старт не ходит в интернет. Как laya хранит веса, выясни сам и запиши в отчёт;
- в образе нет `.env`, `*.sqlite`, `data/cassettes`, `.git`. Это проверяет тест в CI (1.5.4).

**`compose.yaml`:**

| Сервис | Профиль | Команда | Токен | Том |
|---|---|---|---|---|
| `demo` | по умолчанию | `fm synth load` в `FM_DATA_DIR/fm_synth.sqlite` → `fm db stats`. На этапе 2 сюда добавится `fm demo run --synthetic` | не нужен | `fm-data` |
| `fm` | `tools` | любая команда CLI: `docker compose run --rm fm db stats` | из `.env`, если есть | `fm-data` |
| `nightly` | `tools` | сейчас `fm ingest` + `fm index candles` + `fm iss weights`; на этапе 2 заменится на `fm nightly` | обязателен | `fm-data` |
| `fm-ml` | `ml` | как `fm`, но образ `runtime-ml` | из `.env` | `fm-data` |

- `env_file: [{path: .env, required: false}]` у сервисов с токеном. Без `.env` `demo` работает, а `nightly` падает с понятным сообщением `ConfigError`, а не с трейсбеком.
- Образ по умолчанию `ghcr.io/rombintu/factorminus:${FM_TAG:-main}`, рядом `build:` для локальной сборки. `docker compose build` собирает локально, `docker compose pull` берёт готовое.
- Сервис `api` (порт 8000, healthcheck на `/health`) добавит этап 3. Оставь в compose комментарий с этим местом и соглашением: порт, путь проверки здоровья, `depends_on` с `condition: service_healthy`.
- Расписание nightly на сервере: cron хоста (`docker compose run --rm nightly`). Пример строки — в `docs/DEPLOY.md`.

**Makefile:** `docker-build`, `docker-build-ml`, `docker-test`, `docker-demo`, `ca-bundle`, `lock`. Вывод `make docker-demo` на чистой машине — в отчёт.

**`docs/DEPLOY.md`:** как поднять на любой машине (ноутбук, VPS):
- установка Docker;
- `.env` из `.env.example`;
- `docker compose pull && docker compose run --rm demo`;
- загрузка реальных данных;
- cron;
- обновление на новый релиз (`FM_TAG=v0.2.0`);
- бэкап тома `fm-data`;
- что делать, если MCP не отвечает (TLS, токен).

Для Mac на Apple Silicon: образы multi-arch, эмуляция не нужна.

## 1.5.3. CI: `.github/workflows/ci.yml`

Триггеры: `pull_request` (в `main`), `push` в `main`, `workflow_dispatch`. `concurrency` с отменой предыдущего прогона той же ветки. По умолчанию `permissions: contents: read`.

Задачи (jobs). Каждая вызывает цель `Makefile`, YAML только оркестрирует:

| Job | Что делает | Блокирует merge |
|---|---|---|
| `lint` | `make lint` (ruff check + format --check) | да |
| `test` | `make test-cov`: pytest офлайн, покрытие с порогом `--cov-fail-under` = текущее покрытие минус 2 п.п. (замерь и запиши; порог только растёт). Отчёт покрытия в summary | да |
| `hygiene` | `make hygiene` (1.5.4) + gitleaks по всей истории (`fetch-depth: 0`) | да |
| `lockfiles` | lock-файлы соответствуют `pyproject.toml` | да |
| `contract` | `fm contract export` во временную папку и diff с `docs/contract/`: схема в git совпадает с кодом | да |
| `docker` | сборка `runtime` и `test` (buildx, кэш `type=gha`), `make docker-test`, smoke: `docker compose run --rm demo` на синтетике, проверки образа (1.5.4) | да |
| `audit` | `pip-audit -r requirements/base.txt` | нет (предупреждение), пока не разберёмся с ложными срабатываниями; исключения с причиной в `.github/pip-audit-ignore.txt` |

- Python 3.12, кэш pip по хэшу lock-файлов.
- **Сводка прогона** (`scripts/ci_summary.py` → `$GITHUB_STEP_SUMMARY`):
  - число тестов (passed / skipped / failed);
  - покрытие;
  - размер образа;
  - время сборки;
  - результат гигиены.

  Скрипт читает JUnit XML и coverage XML. Это то место, куда этап 2 допишет метрики `fm eval` (контрольные X/10, размеченные, p95 вердикта), а этап 4 — e2e. Сделай расширяемо: секции из файлов `build/ci/*.md`, которые пишут цели Makefile.
- Цель `make ci` локально прогоняет то же, что CI, кроме docker и gitleaks. Это быстрая проверка перед пушем.

**`.github/workflows/ml.yml`:** `workflow_dispatch`, раз в неделю по расписанию и на PR, если изменились `src/factorminus/analysis/labeler*`, `requirements/ml.txt` или `Dockerfile`.
- Собирает `runtime-ml` и в нём запускает `make test-ml`.
- Сейчас в `tests/test_ml_smoke.py` (`@pytest.mark.ml`) один тест: laya импортируется, `Router(preload=True)` загружается без сети (веса уже в образе), один `predict` на фиктивном вопросе возвращает ответ нужного типа.
- Опция pytest `--ml` и маркер `ml` добавляются в `conftest.py` по образцу `--live`. Этап 2 добавит свои тесты под этот маркер.
- В merge не блокирует.

## 1.5.4. Гигиена: секреты и рыночные данные

Репозиторий публичный. Правила CONTEXT (раздел 6) теперь проверяются автоматически.

`scripts/check_repo_hygiene.py` (`make hygiene`, тесты на «да» и «нет») по файлам, которые отслеживает git:
- запрещены `.env` и `.env.*` (кроме `.env.example`), `*.sqlite*`, `*.log`, `data/cassettes/**`, `data/ca/**`, `data/universe_resolved.json`;
- в `data/` разрешены только `*.yaml` (конфигурация: universe, позже episodes, groups, demo_portfolios). Поправь `.gitignore` так же: `data/*` + `!data/*.yaml`;
- нет строк, похожих на токен T-Invest: `t\.[A-Za-z0-9_-]{40,}` (точный шаблон подбери по длине реального токена, **не открывая `.env`**: длину спроси у пользователя или возьми из документации; ложные срабатывания на тестовом `t.***` недопустимы);
- нет файлов больше 1 МБ, кроме явного списка (синтетика `candles.csv`, если она больше);
- в `tests/fixtures/` нет реальных тикеров с ценами: синтетические инструменты начинаются с `SYN_`, а каждый файл кассеты или фикстуры, где встречается не-`SYN_` тикер, есть в явном списке исключений с причиной.

gitleaks: конфиг `.gitleaks.toml` с правилом для токена T-Invest поверх стандартных. Если `gitleaks-action` требует лицензию, запускай бинарник или официальный контейнер gitleaks напрямую.

Проверки образа в job `docker`:
- в образе нет `/app/.env` и `*.sqlite`;
- процесс не root;
- `docker history --no-trunc` не содержит `TINVEST_TOKEN=` с непустым значением;
- `fm mcp check` без токена завершается понятной ошибкой конфигурации, а не трейсбеком.

`.pre-commit-config.yaml`: ruff, ruff-format, `check_repo_hygiene.py`, gitleaks. В `README` одна строка: `pre-commit install`.

## 1.5.5. CD: `.github/workflows/release.yml`

Триггеры: `push` в `main` и теги `v*`.

| Событие | Что публикуется |
|---|---|
| push в `main` | `ghcr.io/rombintu/factorminus:main` и `:sha-<коротк>`, только `runtime` |
| тег `vX.Y.Z` | `:X.Y.Z`, `:X.Y`, `:latest` для `runtime`; `:X.Y.Z-ml` для `runtime-ml`; GitHub Release |

- Multi-arch `linux/amd64` и `linux/arm64`. Для arm64 используй нативный раннер `ubuntu-24.04-arm` (бесплатно для публичных репозиториев) вместо QEMU: torch под эмуляцией собирается очень долго. Манифест объединяется отдельным job.
- Публикация только после зелёного CI на том же коммите (`workflow_run` или `needs` на переиспользуемый workflow; выбери и обоснуй в отчёте).
- `permissions: packages: write` только у job публикации. Вход в GHCR через `GITHUB_TOKEN`, личные токены не нужны.
- SBOM и provenance: `docker/build-push-action` с `sbom: true`, `provenance: mode=max`.
- **Нумерация этапов:** `v0.1.0` — этап 1, `v0.1.5` — этот этап, `v0.2.0` — этап 2, `v0.3.0` — этап 3, `v1.0.0` — Demo Day. Тег вида `stage-1` **не использовать**: он совпадает с именем ветки, и git будет путать ссылки.
- Текст GitHub Release: раздел «Что сделано» из `docs/reports/STAGE_N_REPORT.md` (скрипт `scripts/release_notes.py`, номер этапа — из `docs/STAGES.md`) плюс ссылки на образы и сводку CI.
- **Теги ставит пользователь.** Workflow только реагирует на тег.
- Пакет GHCR по умолчанию приватный. В `docs/CI.md` напиши, как сделать его публичным, если пользователь захочет. Сам не меняй.

## 1.5.6. Контроль этапов

1. **`.github/pull_request_template.md`:**
   - этап и ссылка на ТЗ;
   - ссылка на отчёт;
   - чек-лист:
     - CI зелёный;
     - отчёт с фактическим выводом команд;
     - CONTEXT обновлён, если поменялись правила или данные;
     - нет `.env`, рыночных данных и ответов MCP;

   - для этапа 2 и далее — метрики eval.

   - этап;
   - ветка;
   - PR;
   - тег;
   - статус (`в работе` / `на ревью` / `принят`);
   - отчёт;
   - ключевые метрики.

   Заполни этапы 1 и 1.5. Каждый следующий этап обновляет свою строку.
3. **`.github/dependabot.yml`:** `pip` (`requirements/`), `github-actions`, `docker`. Раз в неделю, группировка мелких обновлений в один PR.
4. **Защита `main`** (ruleset или branch protection):
   - merge только через PR;
   - обязательные проверки `lint`, `test`, `hygiene`, `lockfiles`, `contract`, `docker`;
   - без force push и удаления ветки.

   Это настройка репозитория, поэтому её делает пользователь. Ты пишешь в `docs/CI.md` пошаговую инструкцию и готовую команду `gh api` и применяешь её **только по явной просьбе пользователя**.

   - как добавить проверку для нового этапа: новая цель в `Makefile` → вызов в существующем job → секция в summary. Новый job нужен, только если нужен другой образ или раннер;
   - как читать сводку прогона;
   - как выпустить релиз;
   - почему live-тестов нет в CI.

7. **`README.md`:** бейдж CI, раздел «Быстрый старт в Docker» (три команды), ссылки на `docs/DEPLOY.md` и `docs/CI.md`.

## 1.5.7. Безопасность workflow

- Только `pull_request`, **никогда** `pull_request_target`: репозиторий публичный, PR от чужих форков не должны получать секреты и права записи.
- Все сторонние actions закреплены по полному SHA коммита с комментарием версии (`uses: actions/checkout@<sha> # v4.x.x`). Dependabot их обновляет.
- `permissions` на уровне workflow — `contents: read`. Расширение только в конкретном job и только нужных прав.
- Никаких секретов в CI этого этапа, кроме встроенного `GITHUB_TOKEN`. `TINVEST_TOKEN` в GitHub Secrets **не добавляется**.
- Артефакты CI (покрытие, JUnit, SBOM) не содержат рыночных данных: только синтетика.
- `actionlint` по `.github/workflows/` в job `lint`, `hadolint` по `Dockerfile` (через их контейнеры или закреплённые бинарники).

## Критерии приёмки

1. Локально: `make lint`, `make test`, `make hygiene`, `make ci` зелёные. `make test-live` зелёный (с `.env` пользователя, как раньше).
2. `make docker-build && make docker-test` зелёные. `docker compose run --rm demo` на машине **без `.env`** отрабатывает на синтетике. Вывод в отчёте.
3. `docker compose run --rm nightly` с `.env` пользователя загружает реальные данные в том `fm-data`, а `docker compose run --rm fm db stats` их показывает. Без `.env` — понятная ошибка конфигурации. Вывод (без значений токена) в отчёте.
4. Пересборка образа с изменённым `data/universe.yaml` даёт новую вселенную при существующем томе `fm-data`. Это проверка 1.5.0 п. 2, тестом или командой с выводом в отчёте.
5. `FM_HOME` и `FM_DATA_DIR` покрыты тестами. Локальная работа без этих переменных не изменилась.
6. Подменённый корневой сертификат в `certs/` отвергается скриптом сборки бандла.
7. `make hygiene` ловит подложенные в тесте `.env`, `*.sqlite`, файл в `data/cassettes/`, строку-токен и не ругается на `t.***` и текущее содержимое репозитория.
8. В образе нет `.env` и `*.sqlite`, процесс не root, `TINVEST_TOKEN` не фигурирует в `docker history`.
9. Размеры образов `runtime` и `runtime-ml` и время их сборки записаны в отчёт. Ориентир: `runtime` < 300 МБ.
10. Workflow проходят `actionlint`, Dockerfile — `hadolint`. Все actions закреплены по SHA, `pull_request_target` нигде нет.
11. После разрешения пользователя на push: PR `infra` → `main` открыт, все обязательные проверки зелёные, ссылка на прогон в отчёте. Публикацию `:main` в GHCR проверить можно только после merge. Если пользователь ещё не влил PR, так и запиши.
12. `docs/CI.md`, `docs/DEPLOY.md`, `docs/STAGES.md`, шаблон PR, `dependabot.yml` на месте. `CONTEXT.md` и `README.md` обновлены.
13. Отчёт `docs/reports/STAGE_1_5_REPORT.md`:
    - что сделано;
    - фактический вывод команд;
    - отклонения от ТЗ с причинами;
    - замеры (размеры образов, время CI);
    - открытые вопросы.

## Что НЕ делать на этом этапе

- Не трогать логику анализа и контракт вердикта. Правки в `src/` — только пути (`FM_HOME`, `FM_DATA_DIR`), CA-бандл и то, что нужно для запуска в контейнере.
- Не запускать live-тесты в CI и не класть `TINVEST_TOKEN` в GitHub Secrets. Причины:
  - репозиторий публичный;
  - ответы MCP и реальные цены не должны попадать в логи и артефакты;
  - условия T-Invest запрещают передавать данные MCP третьим лицам;
  - раннеры GitHub находятся за рубежом, доступ к API оттуда не гарантирован.

  Если пользователь позже захочет live-проверку, это отдельный workflow с ручным запуском и окружением с обязательным подтверждением. Опиши этот вариант в `docs/CI.md`, но не делай.
- Не встраивать в образ реальную БД, кассеты с реальными ответами, `.env` и CA-бандл из `data/ca` (бандл собирается из `certs/` при сборке).
- Не настраивать деплой на конкретный сервер по SSH: сервера пока нет. `docs/DEPLOY.md` описывает ручной запуск на любом хосте.
- Не менять настройки репозитория на GitHub (защита веток, видимость пакетов, секреты) без явной просьбы пользователя.
- Не ставить теги релизов самостоятельно.
- Не открывать, не печатать и не копировать `.env`.
